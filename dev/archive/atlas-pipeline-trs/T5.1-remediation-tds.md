## 1. Goal

Close every gap and latent bug discovered during the T5.1 manual E2E run so that **all five success criteria of T5.1 PASS** without manual intervention beyond the documented human gates and the manual `git commit` step inside the worktree.

After this work:
- A T5.1 run end-to-end leaves a single plumb `runs` row with `status='success'` and the full set of expected `spans` + `scores` rows attributed to that `run_id`.
- `atlas resume` after Ctrl-C between `code_gen` and the post-commit hook reattaches to the *same* plumb run; no orphan rows.
- The `awaiting_hook` path can no longer hang indefinitely or race past the commit.
- The post-commit hook stays correct after venv reinstalls.

## 2. Scope

### In scope
- `src/atlas/orchestrator.py` — `run_to_completion`, `step`, `_find_atlas_root`, span-id persistence.
- `src/atlas/plumb_io.py` — `close_run` failure path, `reopen_run` (new), error logging.
- `src/atlas/post_commit_hook.py` — interpreter-path hardening, install-time warnings.
- `src/atlas/state.py` — persist code_gen span_id + commit-wait state in `.atlas/current-run`.
- `src/atlas/cli.py` — wire `reopen_run` into `resume`, optional `--wait-for-commit-timeout`.
- New tests under `tests/unit/` and a single E2E under `tests/e2e/`.

### Out of scope
- Refactor of the 7-stage state machine.
- Plumb internals; we use whatever public API plumb already exposes.
- Multi-run / multi-tenant concerns (still v1).
- Re-running the full T5.1 recipe — that is a separate verification task gated on this TDS landing.

## 3. Problem Recap

From [T5.1-implementation-findings.md](T5.1-implementation-findings.md), the run produced:

| Criterion | Result |
|---|---|
| 1. Single `runs` row, status=success | ❌ pending + zero spans (see below) |
| 2. All expected spans present | ❌ split across two runs |
| 3. All expected scores present | ❌ split / missing |
| 4. `git log main` byte-identical | ✅ |
| 5. Resume protocol works | ✅ functionally, ❌ for plumb attribution |

The findings doc identified the cause as “PlumbIO destroyed on `awaiting_hook` exit.” That is partially fixed — `run_to_completion` now loops through `awaiting_hook` ([orchestrator.py:310-321](../../../src/atlas/orchestrator.py:310)). But three follow-on bugs remain, plus several smaller issues uncovered while reading the current code.

## 4. Issues to Address

### P0 — Blocks T5.1 criteria 1–3

#### P0-1. `awaiting_hook` does not actually wait for the commit
After `code_gen` returns `awaiting_hook`, `run_to_completion` immediately calls `step()` again, which advances to `code_review` because the `code_gen` checkbox is already marked. The post-commit hook then fires *after* `code_review` (or never), so `pending-scores.jsonl` is flushed too late or against the wrong span.

**Fix:** When `step()` returns `awaiting_hook`, `run_to_completion` polls `.atlas/pending-scores.jsonl` for a record matching `ctx.run_id` before continuing. Add `_wait_for_commit_score(run_id, timeout_s)` helper.
- Default timeout: 30 minutes (config-driven via `[gates] commit_wait_timeout_s`).
- On timeout: return early with the run still marked active so `atlas resume` can pick up.
- Poll interval: 2 s (cheap; file is only read).

**Affected:** `orchestrator.py:run_to_completion`, new `_wait_for_commit_score`, `config.py` (new field), `tests/unit/test_orchestrator.py`.

#### P0-2. `atlas resume` cannot reattach to an existing plumb run
[cli.py:42](../../../src/atlas/cli.py:42) constructs a fresh `PlumbIO(real=True)`; `pipeline.resume()` never calls `open_run`, so `_run_handle` stays `None` and every subsequent `record_span` falls back to the in-memory stub list. The original plumb run stays `pending` forever.

**Fix:** Add `PlumbIO.reopen_run(run_id: str) -> str`. Implementation depends on plumb’s public API:
- **Preferred:** plumb exposes a `plumb.reopen(run_id=…)` (or equivalent) returning the same `RunHandle`. Use it.
- **Fallback (Option B in findings doc):** plumb has no reopen primitive. Open a *child* run with `parent_run_id=<original>`, update TRD criterion 1 to allow a parent+child pair, and surface the linkage in `status`.

`cli.resume` calls `pipeline.reopen(ctx)` (new public method) which delegates to `PlumbIO.reopen_run(ctx.run_id)`.

**Affected:** `plumb_io.py` (new method), `orchestrator.py:Pipeline.reopen`, `cli.py:resume`, `tests/unit/test_plumb_io.py`, `tests/unit/test_resume.py` (new).

> **Decision needed before implementation:** Does plumb expose a public reopen API? If not, lock in Option B and update the TRD in the same PR.

#### P0-3. Post-commit hook score loses span attribution on resume
[orchestrator.py:162-166](../../../src/atlas/orchestrator.py:162) flushes pending scores keyed on `self._last_code_gen_span_id`. On resume that field is `""` (fresh `Pipeline` instance), so the score is written with an empty `span_id` and detaches from the `code_gen` span.

**Fix:** Persist `code_gen_span_id` to `.atlas/current-run` (line 3, optional). `StateStore.read_current_run_with_worktree()` returns it; `Pipeline.resume()` rehydrates `self._last_code_gen_span_id`. Backward compatible — older two-line files continue to work.

**Affected:** `state.py` (`write_current_run`, `read_current_run_with_worktree`), `orchestrator.py:Pipeline.resume`, `tests/unit/test_state.py`.

### P1 — Hardens correctness; avoids new failure modes

#### P1-1. `close_run` swallows exceptions on the failure path
[plumb_io.py:70-80](../../../src/atlas/plumb_io.py:70) constructs a `RuntimeError` and passes it to `__exit__`, then catches `Exception` and discards it silently. If `__exit__` returns `True`, the caller can’t tell whether the close succeeded.

**Fix:**
- Always call `__exit__(None, None, None)`; report status separately via plumb’s public status setter (if any) or via a final `add_score`.
- Replace bare `except Exception` with logging through `logging.getLogger("atlas.plumb")` at `WARNING` level.
- Re-raise on success-path errors (corruption is louder than silent loss).

**Affected:** `plumb_io.py`, `tests/unit/test_plumb_io.py`.

#### P1-2. `awaiting_hook` retry loop has no upper bound
If `code_gen` returns `awaiting_hook` repeatedly (e.g. plugin loops, no commit ever lands, P0-1 timeout cycles), `run_to_completion` spins. Add a per-stage `awaiting_hook` attempt counter; abort after 3 with a clear error (`AwaitingHookExceededError`).

**Affected:** `orchestrator.py:run_to_completion`, new exception class, tests.

#### P1-3. `_find_atlas_root` returns a wrong fallback when not in a git checkout
[orchestrator.py:498-512](../../../src/atlas/orchestrator.py:498) walks up looking for a `.git` directory; if none is found it falls back to `Path(__file__).parent.parent.parent`, which silently points at `src/`. Plugins won’t resolve and the failure mode is opaque.

**Fix:** Raise `RuntimeError("atlas must be installed in a git checkout; ran from {…}")`. Document in README that wheel installs are not supported in v1.

**Affected:** `orchestrator.py`, `tests/unit/test_orchestrator.py`.

### P2 — Operational polish

#### P2-1. Hook script silently breaks on venv reinstall
[post_commit_hook.py:94-102](../../../src/atlas/post_commit_hook.py:94) bakes `sys.executable` into the script. If the user later removes that venv, the hook fails with a cryptic shell error.

**Fix:**
- `atlas hook install` warns when `sys.executable` lives outside `<repo>/.venv/`.
- The generated script falls back to `python3 -m atlas.post_commit_hook` with a short `command -v` guard and a one-line error pointing to `atlas hook install`.

**Affected:** `post_commit_hook.py`, `tests/unit/test_post_commit_hook.py`.

#### P2-2. `flush_pending_scores` does not log when records are kept for a different `run_id`
Currently silent ([plumb_io.py:174](../../../src/atlas/plumb_io.py:174)). Add a `logger.info` line; it is the only place a stale record signals trouble.

**Affected:** `plumb_io.py`.

## 6. Detailed Designs

### 6.1 `_wait_for_commit_score`
```python
def _wait_for_commit_score(
    self, *, run_id: str, timeout_s: int, poll_interval_s: float = 2.0
) -> bool:
    """Block until pending-scores.jsonl contains a record for run_id, or timeout.
    Returns True if a matching record arrived, False on timeout."""
    pending = self._repo_root / ".atlas" / "pending-scores.jsonl"
    deadline = time.monotonic() + timeout_s
    while time.monotonic() < deadline:
        if pending.exists():
            for line in pending.read_text().splitlines():
                if line.strip() and json.loads(line).get("run_id") == run_id:
                    return True
        time.sleep(poll_interval_s)
    return False
```

`run_to_completion` integrates it as:
```python
if outcome.status == "awaiting_hook":
    awaiting_attempts += 1
    if awaiting_attempts > _AWAITING_HOOK_MAX_ATTEMPTS:
        raise AwaitingHookExceededError(...)
    if not self._wait_for_commit_score(
        run_id=ctx.run_id, timeout_s=self._cfg.commit_wait_timeout_s
    ):
        # User can resume later; leave run open.
        return ctx
```

### 6.3 `.atlas/current-run` schema (extended)
```
<run_id>              # line 1
```

## 8. Success Criteria for this TDS

1. All P0 tasks merged; T5.1 manual recipe passes criteria 1–3 on a fresh run.
2. `atlas resume` after a Ctrl-C between `code_gen` and the commit produces a single `runs` row (Option A) **or** a parent/child pair tagged in `status` (Option B).
3. No new flaky tests; existing 94-test suite still green.
4. No silent `except: pass` introduced.

## 9. Open Questions

1. **Plumb reopen API** (T2). Need to read plumb’s public surface; if absent, ship Option B and update TRD.
2. **Default `commit_wait_timeout_s`**. 30 min feels right for a human-in-the-loop manual commit, but call out in TRD.
3. **Should `run` block on commit by default?** Today the user can wander off after `code_gen`. Blocking is the right T5.1 behavior; for fully autonomous runs (future) we may want `--no-wait-for-commit`. Out of scope for v1; documented here so we don’t paint ourselves into a corner.
