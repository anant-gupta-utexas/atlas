# Pending Decisions & Clarifications — Phase L2 TRS

Split out from `loop-mode-phase-L2-plan.md` to keep that file under the repo's
800-line file cap. Referenced from the plan's own "Pending Decisions &
Clarifications" section — read that section's one-paragraph pointer first,
then this file for full rationale.

---

1. **Does L2 block on L1's open manual checks (T-L1.1, T-L1.8) before starting?** TRD-v3 §14 lists L2's dependency as simply "L1" — and L1's own context.md established the precedent that manual/off-CI checks don't block the *next* phase's engineering work (L0's T-L0.8/T-L0.9 didn't block L1). This TRS follows that precedent: **L2 does not block on T-L1.1/T-L1.8.** But L2 does inherit their risk directly — `run_one_shot()` under `engine:codex` is the first *automated, unattended* Codex dispatch, and if T-L1.1's cache-semantics question (addend vs. subset) is still unresolved, every Codex-lane `loop_dev` run in L2 keeps writing a potentially ~4×-wrong token count with no human in the loop to notice. **Recommendation:** treat T-L1.1 as a hard precondition specifically for *trusting Codex-lane token data* (not for merging L2's code) — i.e., L2 can ship and dispatch `engine:codex` runs, but `cost-per-landed-PR` analysis (L2's own KPI) should not be run against Codex-lane data until T-L1.1 closes. Options: (a) **(recommended)** proceed as scoped above, flag prominently in STATUS.md; (b) make T-L1.1 a hard blocking gate before L2 starts at all — safer but stalls the whole loop daemon on one off-CI capture task.

2. **Planned-lane scope: first-pass-only, or the full task-by-task implementation loop?** TRD-v3 §3.2 describes the planned lane as producing multiple PRs over multiple loop passes (plan-only PR, then subsequent passes implementing the committed TRS task-by-task, each its own worktree run + `/code-review`). TRD-v3 §14's L2 engineering scope summary does not explicitly scope this down — but TRD-v3 §13 #6 (L2's own exit criterion) only requires *"a `wf:planned` issue yields a plan-only PR... and the loop stops"* — it does not require the task-by-task follow-through to work end-to-end. **This TRS scopes L2 to first-pass-only** (produce the TRS triad, open the plan-only PR, stop) because: (a) it matches §13 #6's literal exit bar, (b) the task-by-task loop needs a *second* triage question ("is this issue's committed TRS ready for its next task?") that isn't designed anywhere in the TRD, and (c) building it now risks exactly the "loop mode becomes a framework" risk TRD-v3 §12 flags, before the simpler one-shot-lane data even exists to validate the driver shape. **Options:** (a) **(recommended)** first-pass-only in L2, full task-by-task loop as an explicit L2.5/early-L3 follow-up TRS; (b) design the full multi-pass loop now, accepting L2 grows substantially past the "~500 lines net" target TRD-v3 §13 #13 sets for the whole loop-mode arc.

3. **How much of the L1 code review's open findings does L2 need to absorb?** The review flagged one Medium (M1, cache-semantics — see Decision #1 above) and four Low/Nit findings. L2 is the first phase where `PrRef` (L1 review finding L2, addressed in T-L2.12), the worktree-vs-`--sandbox` cwd ambiguity (L1 finding L1, needs the T-L1.8 manual smoke check which L2 doesn't own), and the branch-safety exact-match nit (L1 finding L3, `deliverer.py`) become live. **This TRS closes only the `PrRef.number` finding** (T-L2.12) because it's the one L2 code directly, newly depends on. The cwd ambiguity and branch-safety nit are **not** touched by this TRS — they remain L1/L0-owned findings, tracked in BACKLOG.md, not silently absorbed or silently ignored. **Options:** (a) **(recommended)** as scoped — one finding closed because L2 code depends on it, others left explicitly tracked; (b) use L2 as a general cleanup pass and close all four remaining findings now, expanding L2's diff surface beyond the loop daemon itself.

4. **Should `triage.py` be its own file, or inlined into `loop.py`?** Appendix A's seam inventory lists `loop.py` as the one new driver module and doesn't call out a separate triage file. This TRS splits triage into `triage.py` for unit-testability (label-wins-vs-classify is a pure decision function, easy to test in isolation) and to keep `loop.py` from growing past a readable size given `tick()`'s own complexity. **Options:** (a) **(recommended)** separate `triage.py`, ~30-50 lines; (b) inline into `loop.py`, matching Appendix A's literal file list at the cost of a larger single file. Low-stakes; flagged only because Appendix A's "if implementation finds it needs editing beyond what's listed, pause and reconcile" spirit applies loosely to file-count as well as module boundaries — this is a name-only deviation, not a scope deviation, but named explicitly rather than silently done.

5. **`claim()` — one combined `gh issue edit` call or two separate calls (label swap, then assign)?** `gh issue edit <n> --remove-label X --add-label Y --add-assignee Z` supports all three in one invocation. A single call is simpler and reduces the crash window between label-swap and assignment. **Recommendation: one combined call** (implementation detail, not a design fork — noted here only so T-L2.2 doesn't need to re-derive it).

6. **`LoopState` persistence: a JSON file, or (once available) a durable plumb-adjacent store?** TRD-v3 §13 #14 forbids any plumb schema migration in v3.0-v3.2, so plumb is not an option regardless. The real choice is a flat JSON file (`.atlas/loop-state.json`, this TRS's choice) vs. reusing `StateStore`'s existing `tasks.md`-adjacent file conventions (`state.py`). **Recommendation: a new flat JSON file**, because `LoopState` is per-*loop-process* state (budgets, breaker), categorically different from `StateStore`'s per-*run* state (`tasks.md`, `.atlas/current-run`) — conflating them would make `state.py` need to reason about two unrelated lifecycles. Flagged as a decision rather than silently assumed because it's a new persistence mechanism, however small.

7. **Does `queue_gh.py` need its own `preflight()`-style auth check, matching `CliBackend.preflight()`'s pattern?** TRD-v3 §5 states the loop "assumes a working `gh auth` session" but doesn't mandate a startup check the way it does for `CodexBackend`. **This TRS does not add one** — the first `list_ready` call surfaces an unauthenticated `gh` as a natural `GhCliError`, and `run_forever()`'s recoverable-tick-failure handling already covers it (the loop logs and keeps polling rather than crashing, which is arguably *better* UX than a startup fail-closed if the operator authenticates a few minutes after starting the loop). **Options:** (a) **(recommended)** no explicit preflight, rely on first-call failure + recoverable-tick handling; (b) add `queue_gh.preflight()` mirroring `CodexBackend`'s pattern for a clearer startup error message. Low-stakes; (b) is a small addition if the operator experience of (a) proves confusing in practice.

8. **How does `sync_prior_prs()` attach a `user_signal` score to a run that isn't "live" in the current process?** `PlumbIO.record_user_signal()` writes through `self._run_handle`, which only exists while a `plumb_run(...)` context manager is open (`open_run`/`reopen_run`). But `sync()` runs on a *later* tick — possibly a different process entirely (after a restart) — scoring a PR that was delivered several ticks (or loop restarts) ago. Plumb's own child-run/`reopen_run` pattern (used today for atlas's *own* `resume()`) is designed for exactly this "reattach to a previous run and write more" case. **Resolution assumed by this TRS:** `sync_prior_prs()` calls `PlumbIO.reopen_run(run_id)` (already implemented, used by `Pipeline.resume()`) to get a live handle back, writes the `user_signal` score, then `close_run()`s it — treating "post-hoc PR-outcome scoring" as structurally the same operation as "resuming a run to keep writing." This reuses 100% existing plumb surface — **no new `PlumbIO` method is needed**, `reopen_run` already does the job. **Flagged as a decision, not silently assumed,** because reusing "resume a run" semantics for "score a run after the fact" is a slight conceptual stretch worth the maintainer's eyes before T-L2.7 is implemented.

9. **Tie-breaking when multiple repos have ready issues** (relevant once L4 adds a second repo, but the mechanism is chosen now in L2's `pull_next_ready`). This TRS resolves it as first-match-in-`cfg.repos`-list-order, first-issue-in-`gh`'s-own-default-order (oldest-first). No priority/weighting scheme. **Recommendation: accept as scoped** — v3.0-v3.1's `repos` list is length 1 in practice (TRD-v3 §7: "target repos (v3.0: atlas builds atlas)"), so this is inert until L4. Named here so L4's TRS author doesn't need to rediscover where the ordering logic lives.

10. **What exactly goes into `build_issue_prompt()` beyond title + body?** TRD-v3 §3.5's `tick()` sketch mentions *"guardrail signs + existing context_hint"* as prompt inputs beyond the issue text itself, without defining either term further. "Guardrail signs" was resolved in L1 (Resolved Decision #2) to mean `StageOutcome.status`/`RunResult.status` propagation — a *runtime* mechanism, not prompt text. "`context_hint`" has no defined source anywhere in the codebase (`state.py` doesn't have this field; grep-confirmed). **Recommendation:** T-L2.5 implements `build_issue_prompt()` as `f"{issue.title}\n\n{issue.body}"` plus a short fixed preamble reminding the agent to scope to the issue's acceptance criteria (matching `loop_dev.yaml`'s own `code_gen` stage prompt, which already says "Do not touch files outside the stated scope") — no dynamic `context_hint` lookup, since no such mechanism exists yet. Flagged so the maintainer can correct this reading if `context_hint` was meant to reference something specific.

11. **Should `cli.py::_make_pipeline` be refactored into a shared, importable function, or should `loop.py` duplicate its ~15-line construction pattern?** `_make_pipeline` is currently a private (underscore-prefixed) function in `cli.py`. `loop.py` needs the identical construction (same `SubprocessStageRunner`/`CompositeStageRunner`/`Pipeline` wiring), plus a `--backend` override for the `engine:*` label that `_make_pipeline` doesn't currently parametrize (it reads `cfg.default_backend` only). **Recommendation:** extract a shared `make_pipeline()` (drop the underscore, add a `backend_override: str | None = None` param) into a new-or-existing shared location — either promote it out of `cli.py` into `orchestrator.py` alongside `Pipeline` itself, or keep it in `cli.py` and have `loop.py` import the "private" function. **This TRS assumes extraction to a shared location** (T-L2.5's scope) rather than duplication, to honor TRD-v3 §3.5's own claim that "the loop constructs and drives `Pipeline` instances exactly as `cli.py::run` does today" — duplication would let the two drift silently.

12. **Does `relabel(state="done")` also close the issue, or is closing a separate `queue_gh` call?** TRD-v3 §3.1's label table says `atlas:done` means *"the delivering PR merged (issue closed)"* — implying closure is bundled with the `done` transition. **This TRS bundles it**: `relabel(issue, state="done")` performs both the label swap and `gh issue close` as one adapter-level operation, because splitting them would let a crash between the two calls leave an issue `atlas:done`-labeled but still open — a state `reconcile_orphans` has no rule for. Named as a decision because TRD-v3 §3.1's `relabel()` signature sketch doesn't show a close operation, so an implementer following it literally could reasonably split them.

13. **How does the triage classifier actually dispatch its single haiku call — through `SubprocessStageRunner`, or a lighter-weight direct call?** TRD-v3 §3.2 calls it *"a `RAW:`-style single-shot, not an agentic run"* but doesn't specify the dispatch mechanism. Reusing `SubprocessStageRunner.run()` would require constructing a throwaway single-stage workflow just for one classification call. **Recommendation:** call `CliBackend.build_argv()`/`parse_result()` directly (bypassing `SubprocessStageRunner`'s stage/gate/worktree machinery entirely) — `triage.py` imports `make_backend()` from `cli_backend.py` and drives it directly. This keeps the classifier genuinely lightweight and matches "not an agentic run" literally. Flagged because it's a new *pattern* of `CliBackend` usage (outside `SubprocessStageRunner`) that doesn't exist yet in the codebase — worth the maintainer's confirmation before T-L2.4 locks it in.

14. **What happens to an issue whose `loop_dev` run failed, or whose successful run failed to deliver — does it just sit `atlas:working` forever?** TRD-v3 explicitly defers self-healing to L3, so "just sit there" for L2 is arguably correct-per-scope — but it means a failed run produces **no PR, no comment, no visible signal to the operator** beyond the issue remaining `atlas:working` past when they'd expect a PR. **Recommendation:** even without retry logic, T-L2.5 should have `tick()` post a `comment()` on failure too (not just on success) — e.g. *"loop_dev run `<run_id>` failed (status=failure); issue left `atlas:working` for manual retry or investigation"* — so the operator has a signal without needing to check `atlas loop status` or plumb directly. **Options:** (a) **(recommended)** always comment, success or failure; (b) comment only on success, matching the TRD sketch literally, deferring failure-visibility to L3's self-healing/judge work.

15. **Should "`loop.py` never shells `gh` directly" be enforced by a grep-based test, or left as a code-review convention?** TRD-v3 §6 states this as a boundary guarantee. A grep-based CI test is cheap and mirrors the "assert the dangerous call never fires" security-test pattern L0/L1 both used for `Deliverer`/`preflight()`. **Recommendation: yes, add it** — cheap, and it converts an architectural guarantee into something CI actually enforces. Included as an implicit acceptance criterion under T-L2.2.

16. **`trusted_authors` enforcement: what happens to a dispatch refused because the issue author isn't trusted — silently skip, relabel, or block the whole tick?** Low-stakes today (default `trusted_authors=()` is inert), load-bearing the moment a repo becomes public. **Recommendation:** an untrusted-author issue is skipped for this tick (not claimed, not dispatched, not relabeled away from `atlas:ready`) and logged as a warning — leaving it visibly `atlas:ready` so a human notices it's stuck. `pull_next_ready` should skip past it to the next ready issue (if any) rather than treating "found an untrusted issue" as equivalent to "no ready issue." Flagged because relabeling it `atlas:blocked` could look confusingly similar to a self-healing exhaustion state that doesn't exist until L3.

17. **Does the triage classifier's token cost count toward `max_dollars_per_day`?** **Recommendation:** yes, if measurable (via Pending Decision #13's resolution) — folding it in keeps the budget cap honest about *all* LLM spend the loop causes. It should **not** count toward `max_runs_per_day`, since that cap bounds the number of *code-changing* runs, not classification calls.

18. **`run_forever`'s exception boundary — how broad is the catch-all around a single `tick()` call?** `tick()` already catches the specific exceptions it expects (`GhCliError`, `DeliveryError`, `AbortedError`) internally. The open question is whether `run_forever()` should *additionally* wrap each `tick()` call in a bare `except Exception` as a last-resort safety net. **Recommendation: yes** — an unattended, long-running process should never die from one tick's unhandled exception. The cost of "swallowing a bug and it recurs every tick" is bounded by the circuit breaker (a repeated identical exception trips `identical_error_limit`); the cost of "the daemon silently died three hours ago and nobody noticed" is unbounded.
